**Scope contract (frozen).** Get SmartSpeak into 12 closed testers' hands this week without regressing
anything already device-verified. **In scope:** correctness bugs a tester hits in their first session,

### Corrections made to the delegated reviewer's report

Never relayed on faith — both caught by re-deriving its claims:

1. It reported the download as **62 MB** by summing `ort-wasm.wasm` *and* `ort-wasm-simd.wasm`. Only one
   loads per device. The honest figure is **~55 MB**, which is what shipped in the copy.
2. It recommended warming the model up on `/train` mount instead of at recording start. **Rejected** —
   that would spend 55 MB of a tester's mobile data on someone merely browsing the module list. The
   existing design (download overlaps the take) is already the better trade.

### Inspected and found good (protect from churn)

- **Mic permission handling** (`player.tsx:402-416`) — distinct, actionable copy per `NotAllowedError` /
  `NotFoundError` / `NotReadableError`, including the exact Android Settings path.
- **Recording lifecycle** — the 29/07 `takeCommittedRef` work is correct: an abandoned take never scores
  or burns a free slot, a committed take is never dropped mid-teardown.
- **Storage resilience** (`local-store.ts:84-125`, `calibration.ts`, `entitlement.ts:35-51`) — every
  read/write wrapped, numerics clamped, safe fallback on both empty and corrupt storage.
- **Service worker** (`sw.js:21-41`) — `skipWaiting()` + `clients.claim()` + network-first shell. This is
  the *opposite* of the stale-pin risk that was suspected; testers get fresh code each session, which is
  exactly what a TWA-over-Netlify needs.
- **Security headers** (`_headers:5,8`) — `Permissions-Policy: microphone=(self)` and a CSP that permits
  `worker-src 'self' blob:` with `connect-src 'self'`, consistent with fully self-hosted models
  (`env.allowRemoteModels = false`) — no CDN to fail on a flaky connection.
- **`assetlinks.json`** — present, with both the upload-key and Play-App-signing SHA-256 fingerprints.
- **`STORE_LIVE = false`** — correctly left alone. It only routes plain-browser visitors, and the public
  listing 404s until production; flipping it now would swap an honest message for a dead link.

## P4 — Gap closure

### G1 — the pre-launch grace (the whole point of this run)

Four options were put to the Fable 5 advisor: ship as-is, temporarily raise `FREE_EXERCISE_LIMIT`,
degrade the button honestly, or grant the app while it is unbuyable. **Chosen: grant while unbuyable,
driven by Play's own state rather than a flag.**

`productState(service)` asks Play whether `pro_unlock` exists and returns one of three states:

| State | Meaning | Effect |
|---|---|---|
| `'available'` | Play knows the product | Paywall enforced, normal purchase flow |
| `'absent'` | Play answered, no such product | **Pre-launch grace — Pro granted** |
| `'unknown'` | No `getDetails`, non-array response, or a throw | **Fails closed — nothing granted** |

`refreshEntitlement()` grants only on an explicit `'absent'`. Every entitlement surface in the app
already called `refreshEntitlement()` on mount (`train/page.tsx:49`, `module/[id]/view.tsx:39`,
`profile/page.tsx:24`, `unlock/page.tsx:50`, `player.tsx:196,209,292`), so that one function was the
minimal-diff insertion point — **no call site changed.**

**Why this beats a flag:** it reverts itself. The moment Tom activates `pro_unlock` in Play Console,
`getDetails` starts returning the product, `'absent'` stops firing, and the real paywall takes over —
no code change, no constant to remember weeks later. A code comment is not a mechanism; Play's own
state is.

**Revenue-leak delta: none of consequence.** The app already trusts a user-writable `localStorage` flag
(`smartspeak.pro.v1`) as its entitlement cache — a documented, accepted trade-off of the TWA
architecture (playbook risk table). This change alters *when* that same flag is written, not the trust
model, and the window closes permanently once the product goes Active.

### G2 / G3 — the first-session experience

- **G2:** the intro screen now warns before the first take only — gated on *no take existing anywhere on
  the device*, so it appears exactly once and never nags. Copy names the size, the reason (privacy —
  everything runs on-device), and the Wi-Fi advice.
- **G3:** a screen wake lock is acquired after `setPhase('recording')` and released in both
  `releaseWakeLock()` call sites — `cleanup()` (close / retry / unmount) and `stopRecording()` (the normal
  path, which does *not* route through `cleanup`). A `wantWakeLockRef` guard drops the lock if the
  asynchronous `request()` resolves after the take already ended, so a lock is never pinned on the results
  screen.

### G6 — why this is only *partially* closed

Removed from all working-tree files, and both docs now say explicitly never to record it in the repo.
**But git history is immutable and already pushed** — the password remains readable in commit `2407158`
on a public remote. Scrubbing HEAD stops further spread and casual discovery; it does not undo the
exposure.

The remaining work is Tom's, and it is a Play Console action, not a code change: **playbook Step 1b** now
walks through requesting an upload-key reset. Play App Signing makes the upload key replaceable without
losing the app or its users — the app-signing key users actually verify against is held by Google and is
unaffected. History rewriting was **deliberately not attempted**: it is destructive, it is his call on a
public repo that may already be cloned or indexed, and it would not help anyway since the value must be
treated as compromised regardless.

Sequencing judgement: this does **not** block starting the closed test. The password alone is not
exploitable without the keystore file, and the 14-day clock is the scarce resource. Rotate during the test.

### G5 — the operational consequence

`docs/PLAY-LAUNCH-PLAYBOOK.md` Step 10 now carries an explicit warning box: **do not activate
`pro_unlock` until closed testing finishes**, because doing so switches the paywall on for all testers
mid-test. The status table entry changed from ❌ *Not done* to ⏸ *Deliberately not done*.

**G1 is pinned by five new tests**, three of which exist solely to prove the fail-closed rule:

| Case | Expected |
|---|---|
| Play reports the purchase owned | granted |
| Not owned, `getDetails` → `[]` | **granted** (the grace) — and the flag is actually persisted |
| Not owned, `getDetails` → a real product | **not granted** — the paywall still bites once the product is real |
| `getDetails` throws | **not granted**, flag not written |
| `getDetails` returns a non-array | **not granted** |

The grace test is non-tautological: against the pre-change `writeFlag(owned)` it returns `false` and fails.

**G3's optional chain was verified empirically in Node**, not assumed — `nav.wakeLock?.request?.('screen').then(…).catch(…)` short-circuits to `undefined` when `wakeLock` or `request` is missing, so an older Android WebView cannot throw on it.

**Not verified here (honest gaps — all require a real device):**
- The actual runtime behaviour of tapping Unlock in the TWA against a genuinely unregistered SKU. The
  grace should mean no tester ever reaches that button, and `purchasePro()` carries a defence-in-depth
  `'absent'` check for a tap that races the mount-time refresh — but the native failure mode is unproven.
- Whether Android truly suspends audio capture on screen-off, i.e. whether G3 was a live bug or only a
  latent one. The fix is harmless either way.
- Real-world model-download time on a tester's mobile connection.
- The 29/07 run's F2/F3 browser-lifecycle fixes remain device-unverified. **Still the top on-device check:**
  (a) start a take → "✕ Close" mid-recording → no new rep in Progress, free-rep count unchanged;
  (b) start a take → "Stop & get feedback" → immediately "✕ Close" → the rep *does* appear.

## Guardrail that shaped this run

The advisor's answer to "how does RR make this worse?" was **scope creep disguised as thoroughness** —
an unbounded refinement pass over a Next.js app days before recruiting testers surfaces real but
low-priority findings, and fixing them burns the day that should start the 14-day clock while risking
regressions in code already device-verified twice. Adopted rule: **every changed line traces to a
finding that a tester would hit in their first session.** Three of the reviewer's six findings
(`dvh` fallbacks, transcription-timeout copy, backgrounded-worker recovery) were logged and **not
fixed** for exactly this reason.

## Residual risks

- **`player.tsx` is ~1100 lines** and owns recording, transcription, scoring, persistence, achievements,
  paywall state and now the wake lock. Splitting it is the highest-value structural work left, and it is
  the right first task *after* testers are recruited, never before.
- **The suite covers logic, not surfaces.** 94 tests, none of them touching React components, MediaRecorder,
  or the real Digital Goods API. The G1 tests mock the billing service — they prove the decision logic,
  not that Play behaves as assumed.
- **The grace depends on an assumption about the Digital Goods API**: that `getDetails` on an unknown item
  ID resolves to an empty array rather than throwing. If Play throws instead, `productState` returns
  `'unknown'`, the grace does not fire, and testers are back to the G1 dead end — failing *safe* for
  revenue but *badly* for the test. **This is the single thing to confirm on-device before sending out
  opt-in links:** install, burn 3 reps, and check that rep 4 opens instead of showing the paywall.
- **Play Billing ≥8.0.0 remains blocked upstream** with a hard 31/08/2026 deadline. Re-check
  `dl.google.com/dl/android/maven2/com/google/androidbrowserhelper/billing/maven-metadata.xml` for a
  release above 1.1.0 by mid-August. Untouched by this run, by design.
- **`STORE_LIVE = false`** still needs flipping at production rollout (Step 12), not before.
- The Play Console app is still priced **PAID at $13.99**, which blocks all closed testers. That is a
  console action, not code — playbook PART 6.5, and it is irreversible in the direction Tom wants to go.

## Fresh-eyes reconciliation (blind Sonnet critic on the diff)

Per RR, the blind critic's findings outrank self-critique. It independently ran the suite,
`tsc --noEmit` and lint, and read the recording lifecycle end to end.

1. **F2's first fix was too blunt — adopted, F9 below.** Its #1 finding: `recorder.stop()` fires
   its `stop` event as a *queued task*, so nulling the handlers in `cleanup()` unconditionally meant
   any teardown landing in that gap dropped a **finished** take silently — no score, no XP, no
   streak. Most reachable trigger: tapping "✕ Close" immediately after "Stop & get feedback", since
   Close calls `cleanup` directly. Verified and correct: the first fix traded a wrongly-recorded
   take for a wrongly-dropped one, which is the worse failure because it is silent.
2. **Object-URL fix (F3), the `emptyProgress()` factory (F7), the Filler-Free guard (F4) and the
   `require` removal (F8) all verified correct** against the pre-diff code, with the tests confirmed
   non-tautological. Recorded here so future edits don't undo them.
3. **Test suite: category reported clean** — no shared mutable state between cases (the mid-body
   `installStorage()` calls are deliberate resets between an unlocked/not-unlocked assertion pair),
   no tautological assertions.
4. **Not adopted:** the critic noted `stopRecording()` still doesn't null `recorderRef`/`streamRef`,
   unlike the new `cleanup()`. Left as-is deliberately — nulling `recorderRef` there would break the
   committed-take path the F9 fix depends on, and it is pre-existing, harmless (later `cleanup()`
   calls on stopped objects are idempotent) and outside the findings log.

| ID | Area | Finding (evidence) | Impact | Effort | Lev | Status |
|---|---|---|---|---|---|---|
| F9 | Correctness (regression introduced by F2's fix) | Detaching the recorder's handlers on every teardown dropped a **committed** take if unmount raced the queued `stop` event (`player.tsx` `cleanup`/`stopRecording`) | **H** | L | **H** | CLOSED |

**F9's closure.** Teardown now distinguishes the two cases with `takeCommittedRef`, set in
`stopRecording()` and reset in `startRecording()`: an *uncommitted* take still has its handlers
detached (closing mid-recording never scores a rep or burns a free slot), while a *committed* take
keeps them so the queued `stop` event still runs and the rep is scored. Closing that also exposed a
second-order leak — a post-unmount `onstop` would mint a fresh object URL with no cleanup path left
to revoke it — so `onstop` now skips the URL when `unmountedRef` is set while still running
`finishAnalysis`, keeping the take scored.

## Pre-mortem

Six months from now this run failed because the test suite gave false confidence: it covers the
deterministic core beautifully and none of the browser lifecycle, which is exactly where F2 and F3
lived. The mitigation is the on-device check named above — a green `pnpm test` is not evidence that
closing mid-take behaves.
